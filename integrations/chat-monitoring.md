# Assistych. Мониторинг чатов: подключение и интеграция с таск-менеджером

Версия 07.10.2026

## 1. Что делает модуль

Мониторинг чатов читает рабочие группы Telegram и MAX, в которых вы общаетесь с клиентами. Когда в группе происходит событие, требующее внимания проджекта, Assistych создаёт сигнал и передаёт его в ваше приложение. Бот в группы ничего не пишет: он только читает.

Схема работы:

```
группа с клиентом  ->  Assistych  ->  сигнал  ->  ваше приложение (задача)
                                                          |
                         отметка "в работе / решено"  <---+
```

Сигнал создаётся в четырёх случаях: клиент недоволен, клиент спрашивает про оплату, клиент просит отчёт, клиент задал вопрос и сотрудник не ответил в рабочее время. Подробности в разделе 4.

## 2. Подключение групп Telegram

Подключает группу администратор этой группы. Это сделано намеренно: иначе любой участник группы, где уже есть наш бот, мог бы забрать переписку в свой кабинет.

Шаги:

1. Откройте в кабинете Assistych страницу «Мониторинг чатов» (раздел «Магазин», карточка «Мониторинг чатов»).
2. В блоке «Добавьте бота в группу» нажмите «Добавить в группу». Откроется Telegram.
3. Выберите группу с клиентом. Бот добавится в неё и сам привяжет группу к вашему кабинету. Ссылка одна на все группы, ею можно подключать группу за группой.
4. Если бот уже находится в группе, администратор группы отправляет в неё команду из блока «Если бот уже в группе». Она выглядит так: `/connect@AssistychBot cm_<код>`. Готовую команду можно скопировать кнопкой «Скопировать команду».
5. В Telegram делать бота администратором не нужно: он видит все сообщения группы и так. Если в какой-то группе бот видит не всё, она будет помечена в списке групп как «видит не всё» (поле `sees_all_messages: false` в API). Только тогда сделайте бота в этой группе администратором, все права администратора при этом можно выключить. В MAX администратор нужен всегда (см. «Группы MAX» ниже).
6. В блоке «Отметьте своих» впишите юзернеймы сотрудников агентства, по одному в строке, и нажмите «Сохранить сотрудников». Сообщения сотрудников не считаются сообщениями клиента. Тот, кто добавил бота по ссылке, уже отмечен.
7. В списке групп (вкладка «Группы») можно вписать название клиента, как оно записано в вашей таблице. Оно попадёт в сигнал в поле `client.name`.

Что видно в кабинете. Вкладка «Сигналы» показывает ленту сигналов с фильтрами «Открытые» и «Все». Вкладка «Группы» показывает список групп со статусом: «активна», «отключена» (отключили вы кнопкой «Отключить») или «бота удалили». Переписка группы открывается для чтения.

Приватность бота. Режим приватности у бота Assistych выключен, поэтому в Telegram он видит все сообщения без статуса администратора. Если бот был добавлен в группу очень давно и сообщений не видит, удалите его и добавьте снова либо сделайте администратором.

Группы MAX. Ссылки «добавить в группу» у MAX нет. Добавьте бота в группу по имени, сделайте его администратором с правом читать все сообщения и отправьте в группу команду `/connect cm_<код>`. Отправлять должен администратор группы. Бот ничего не ответит, группа появится в списке через несколько секунд. Старую переписку MAX боту не отдаёт.

Код привязки можно сменить в кабинете. После смены старый код перестаёт привязывать новые группы, уже подключённые остаются.

То же из приложения по API. Заходить в кабинет не обязательно, всё кроме самой привязки делается из вашего приложения по ключу API (раздел 6):

- ссылку «Добавить в группу» и команду `/connect` приложение получает запросом `GET /monitor/settings` (поля `connect_link` и `connect_command`, для MAX поле `max`) и показывает проджекту. Добавить бота в группу по ссылке или отправить команду должен администратор группы в Telegram или MAX: по API группу привязать нельзя, так подтверждается право администратора на переписку;
- сотрудников агентства («наших») задаёт `PATCH /monitor/settings` с полем `staff`;
- название клиента и отключение группы: `PATCH /monitor/chats/{id}` с полями `client_name` и `status` (`active` или `disabled`);
- новый код привязки: `POST /monitor/settings/rotate-code`.

Новая группа появляется в `GET /monitor/chats` через несколько секунд после привязки.

## 3. Импорт истории переписки

Бот видит сообщения только с момента добавления. Более раннюю переписку можно загрузить из экспорта Telegram Desktop. Такие сообщения помечены в кабинете «из истории», а в API имеют `"source": "import"`. Сигналов по ним не создаётся.

Как выгрузить:

1. Нужна программа Telegram Desktop для компьютера. В мобильных приложениях и в версии для macOS из App Store такого экспорта нет.
2. Откройте «Настройки», затем «Продвинутые настройки», затем «Экспорт данных Telegram».
3. Оставьте включёнными только «Частные группы» и «Публичные группы». Личные чаты, чаты с ботами, каналы, информацию об аккаунте и контакты выключите. Фото, видео и файлы не нужны.
4. Выберите формат «Машиночитаемый JSON». Если нужна не вся история, задайте дату «С».
5. Нажмите «Экспортировать». Получится файл `result.json`.

Если вы недавно входили в Telegram на этом компьютере, Telegram не начнёт экспорт сразу: он предложит повторить запрос с этого же компьютера позже, обычно через сутки.

Куда загрузить. На странице «Мониторинг чатов» есть два способа.

- Одна группа: во вкладке «Группы» откройте группу и нажмите «Загрузить историю». Формат: `result.json` экспорта одного чата.
- Все группы одним файлом: блок «История до бота: все группы одним файлом», кнопка «Выбрать файл result.json». Файл читается на вашем компьютере. Личные чаты, каналы и боты никуда не отправляются: в кабинет попадают только сообщения групп, которые уже подключены к боту. Пока идёт загрузка, вкладку закрывать нельзя. Если загрузка прервалась, выберите тот же файл ещё раз: загруженные группы пропустятся, остальное догрузится.

Ограничения. Для загрузки одной группы размер файла не больше 20 МБ. Если файл больше, выгрузите историю без медиа или за период. Группа должна быть уже подключена к боту, иначе импорт вернёт ошибку `CHAT_NOT_CONNECTED`. Если файл не является JSON-экспортом Telegram Desktop, будет ошибка `BAD_FILE`. Фото, видео и файлы из экспорта не загружаются: в API у них `media.state` равен `unavailable`.

Что получится. Сообщения появятся в переписке группы и будут доступны через API. В конце загрузки отмечаются сотрудники: если больше всех в истории писали люди, не отмеченные как «наши», кабинет покажет их имена. Если это сотрудники агентства, добавьте их в список.

То же из приложения по API. Результат такой же, как при загрузке из кабинета.

- Одна группа: `POST /monitor/import`, в поле `file` файл `result.json` экспорта одного чата (до 20 МБ). Повтор того же файла ничего не задваивает.
- Все группы из полного экспорта: файл целиком не отправляйте, в нём личные чаты. Сначала `POST /monitor/import/match` со списком `id` и `type` всех чатов экспорта: в ответе отмечены подключённые. Затем для каждой подключённой группы отправьте её сообщения в `POST /monitor/import` с полем `final=false`, большую группу частями от старых сообщений к новым. В конце один раз `POST /monitor/import/finish`: в ответе `top_unmarked`, те, кто много пишет и не отмечен «нашим».

У загрузки свой лимит: 10 запросов в минуту, общий лимит API она не расходует. Ошибки те же, что в кабинете: `CHAT_NOT_CONNECTED`, `FILE_TOO_LARGE`, `BAD_FILE`, `FULL_ACCOUNT_EXPORT`.

## 4. Сигналы

Вид сигнала передаётся в поле `signal_type`. Какие виды ловить, владелец включает в кабинете: «Мониторинг чатов», блок «Что ловить». По умолчанию включён только `negative`.

| `signal_type` | Название в кабинете | Когда создаётся | Как определяется |
|---|---|---|---|
| `negative` | Негатив | Клиент недоволен, жалуется, грозит уйти, язвит в адрес агентства | ИИ по пачке новых сообщений клиентов |
| `payment_due` | Оплата | Клиент спрашивает про счёт, сумму, срок оплаты, обещает оплатить, просит отсрочку или продление. Сообщения «оплатили», «платёжка во вложении» и пополнение кошелька Авито сигнала не дают | ИИ |
| `report_request` | Просят отчёт | Клиент просит отчёт, статистику, цифры или итоги за период | ИИ |
| `question_unanswered` | Вопрос без ответа | Клиент задал вопрос или о чём-то попросил, а сотрудник не ответил дольше N рабочих часов | Таймер, `confidence` равен `null` |
| `staff_tone` | Тон сотрудника | Сотрудник агентства пишет клиенту с раздражением, упрёком, давлением, перекладывает работу на клиента («это ваша задача», «сделайте сами») или грубит. Деловые требования, короткие ответы и шутки сигнала не дают | ИИ по сообщениям сотрудников, `sender` в сигнале — сотрудник |

Правила:

- Пачка сообщений классифицируется после 3 минут тишины в группе или после 20 сообщений. Виды по сообщениям клиента определяются одним вызовом модели, `staff_tone` отдельным. Сигнал создаётся при уверенности модели не ниже 0,6, для `staff_tone` не ниже 0,7.
- «Сотрудник» для `staff_tone` и для ответа на вопрос — это человек из списка `staff` в настройках (раздел 6). Подрядчиков и авитологов, которые пишут клиентам, тоже внесите в `staff`, иначе их сообщения считаются клиентскими и тон по ним не проверяется.
- Для `question_unanswered` N задаётся в кабинете в поле «Сигнал через, рабочих часов» (по умолчанию 4, от 1 до 72). Рабочее время: будни по Москве, по умолчанию с 10:00 до 19:00. Часы меняются через API: `PATCH /monitor/settings` с полями `work_start` и `work_end` (раздел 6). Любое сообщение сотрудника в группе после вопроса снимает ожидание.
- Пока по группе есть открытый сигнал (`new` или `in_work`), новый сигнал того же вида не создаётся. Повторы считаются в поле `repeats` открытого сигнала. Сигналы разных видов друг другу не мешают.
- Закрытый сигнал (`done` или `dismissed`) снимает это ограничение: следующий случай даст новый сигнал.
- `question_unanswered` закрывается сам, когда сотрудник написал в группе после вопроса: статус `done`, в `comment` строка «Закрыт автоматически: ответил Дарья @daria 16.10 16:20 МСК», в API `auto_closed: true`. Остальные виды сами не закрываются: решает проджект. Чтобы проджект не делал лишнюю работу, в сигнале есть поле `already_answered`: кто из сотрудников уже написал в группе после сообщения клиента к моменту создания сигнала.

Откуда задержка сигнала. От сообщения в группе до задачи у вас проходит:

1. 3 минуты тишины в группе: пока переписка идёт, пачка копится, чтобы оценивать разговор целиком, а не каждую реплику. Если тишины нет, пачка уходит на 20-м сообщении.
2. До 1 минуты: проверка идёт раз в минуту.
3. Несколько секунд на ответ модели. Если для бизнеса включён разбор голосовых или фото, пачка ждёт расшифровку до 15 минут.
4. Вебхук отправляется в той же проверке, сразу после создания сигнала. Если вы забираете сигналы опросом `GET /monitor/signals`, добавьте интервал опроса: при опросе раз в 5 минут это ещё до 5 минут.

Итого обычно 4-5 минут после последнего сообщения при вебхуке и до 9-10 минут при опросе раз в 5 минут. За это время сотрудник иногда уже успевает ответить: смотрите `already_answered`. Сигнал `question_unanswered` по смыслу приходит не раньше, чем через N рабочих часов.

Важно. Если ваше приложение написано по версии от 28.09.2026 и не смотрит на `signal_type`, сначала научите его различать виды, а потом включайте остальные. Иначе сигнал «Оплата» придёт задачей «Негатив».

Статусы сигнала: `new` (только что создан), `in_work` (проджект взял), `done` (решено, в том числе автоматически, см. `auto_closed`), `dismissed` (ложное срабатывание; по таким случаям мы улучшаем распознавание).

## 4а. Проджекты: как разделить группы и сигналы

У каждой группы есть проджект: сотрудник агентства, который ведёт этого клиента. Он приходит в поле `project` у группы, у сигнала и в вебхуке, поэтому сигналы можно раздавать по проджектам без ручного разбора.

Как определяется проджект группы:

1. Задан руками. `PATCH /monitor/chats/{id}` с телом `{"project": "@kkotri"}`. Так делайте, если проджект известен заранее, например по брифу продажника. В ответе `project_source` равен `manual`.
2. Иначе автоматически. Проджектом считается тот из списка `projects` в настройках, кто первым написал в группе. Учитывается вся переписка, в том числе загруженная история. Так работает правило «кто ответил после продажника, тот и проджект»: продажник может отметить в сообщении обоих проджектов, проджектом станет тот, кто ответил первым. Продажника в `projects` не включайте. Если список `projects` пуст, проджектом считается тот из «наших» (`staff`), кто больше всех писал в группе за последние 30 дней. В ответе `project_source` равен `auto`. Если никто из них в группе не писал, `project` и `project_source` равны `null`.

Чтобы вернуть группу на автоматический выбор, отправьте `{"project": null}`.

Проджект записывается в сигнал в момент его создания и потом не меняется. Если группу передали другому проджекту, укажите его руками (`PATCH /monitor/chats/{id}`): новые сигналы пойдут новому, а уже созданные останутся у прежнего.

Ник указывается так же, как в `staff`: `@username`, `username` или числовой id. В ответах юзернейм приходит в нижнем регистре и с `@`, например `@smmaleksandr`. Проджекты из `projects` автоматически добавляются в «наши».

Как отметить всех сотрудников. Автоматический выбор и сигналы «без ответа» работают правильно, только если все сотрудники агентства (проджекты, авитологи, продажники, руководитель) есть в `staff`. Иначе их сообщения считаются сообщениями клиента. В загруженной истории Telegram у отправителя есть только id без ника. Assistych сам узнаёт ники через Telegram в течение нескольких часов после загрузки, но надёжнее отметить своих по списку отправителей:

1. `GET /monitor/senders` возвращает всех, кто писал в группах за 60 дней. У каждого есть `name`, `username`, `external_user_id`, `messages`, `chats`, `is_staff` и `staff_key` (ник, а если ника нет, то `id:<число>`).
2. Выберите сотрудников по именам и отправьте их `staff_key` одним запросом `PATCH /monitor/settings` с полем `staff`. `staff` заменяет список целиком, поэтому включите в него и тех, кто уже отмечен (`is_staff: true`).

Пример: два проджекта делят группы.

```
# 0. Кто пишет в группах: отметить своих в staff по staff_key
curl -H "X-API-Key: $ASSISTYCH_API_KEY" "https://assistych.ru/api/v1/monitor/senders"

# 1. Кто у нас проджекты: проджектом группы станет тот из них, кто написал в ней первым
curl -X PATCH -H "X-API-Key: $ASSISTYCH_API_KEY" -H "Content-Type: application/json" \
  -d '{"projects": ["@SMMAleksandr", "@kkotri"]}' \
  "https://assistych.ru/api/v1/monitor/settings"

# 2. Посмотреть, кому досталась какая группа
curl -H "X-API-Key: $ASSISTYCH_API_KEY" "https://assistych.ru/api/v1/monitor/chats"
#   "title": "Ромашка", "project": "@smmaleksandr", "project_source": "auto"

# 3. Поправить руками, где автомат ошибся (например, новая группа после брифа)
curl -X PATCH -H "X-API-Key: $ASSISTYCH_API_KEY" -H "Content-Type: application/json" \
  -d '{"project": "@kkotri"}' \
  "https://assistych.ru/api/v1/monitor/chats/<chat_id>"

# 4. Каждый проджект забирает только свои открытые сигналы
curl -H "X-API-Key: $ASSISTYCH_API_KEY" \
  "https://assistych.ru/api/v1/monitor/signals?status=new,in_work&project=@kkotri"

# сигналы групп без проджекта, их нужно распределить
curl -H "X-API-Key: $ASSISTYCH_API_KEY" \
  "https://assistych.ru/api/v1/monitor/signals?status=new&project=none"
```

В вебхуке `signal.created` проджект лежит в поле `project`. По нему приложение сразу ставит задачу нужному человеку.

## 4б. Аналитика по сотрудникам

`GET /monitor/staff-stats?days=30` показывает по каждому сотруднику агентства, как он работает в группах: как быстро отвечает клиенту, сколько раз клиент его торопил, были ли дни без ответа и какие сигналы были в его группах. По этим цифрам ваша программа может поставить авитологу теги, например «Быстро отвечает» или «Задерживает задачи». Решение о теге остаётся за вашей программой, ниже даны пороги для начала.

`days` от 1 до 90, по умолчанию 30. Обновлять достаточно раз в сутки.

Перед первым запросом отметьте всех сотрудников в `staff` (раздел 4а). Сообщения человека, которого нет в `staff`, считаются сообщениями клиента, и цифры получаются неверными. Поле `possible_staff` в ответе подсказывает, кого вы, возможно, забыли отметить: людей, которые пишут в трёх и более группах или назвались авитологом или куратором. Их `staff_key` добавьте в `staff`. Проджектов добавьте в `projects`, иначе проджект может попасть в авитологи группы.

Как считается:

- Авитолог группы: тот из «наших», кто больше всех писал в группе за период, кроме проджектов из `projects` и проджекта, назначенного этой группе вручную. Показатели «в его группах» считаются по этим группам (поле `avitolog_of`).
- Скорость ответа (`reply`): от сообщения клиента до следующего сообщения любого сотрудника в той же группе. Ожидание считается в рабочих минутах (`work_start`, `work_end` в настройках, будни по Москве): если клиент написал в 17:50, а ответ пришёл в 9:20 следующего дня, при рабочем времени с 9:00 до 18:00 это 30 минут. Вопрос, заданный вечером или в выходной, ждёт с начала рабочего дня: написал в пятницу в 19:00, ответ в понедельник в 15:00 — это 6 часов. Ответ, пришедший до начала рабочего дня, в скорость не попадает. Ответ засчитывается тому, кто ответил.
- Сообщения вроде «ок», «спасибо», «понял», «хорошо, жду», эмодзи и стикеры ответа не требуют и в скорость ответа не попадают.
- `median_minutes`: обычное время ответа (медиана). `over_1h_share`: доля ответов позже часа. `replies`: сколько ответов посчитано.
- `waiting_now`: в скольких его группах клиент сейчас ждёт ответа больше часа рабочего времени (на момент запроса).
- `reminders`: сколько раз клиент торопил или напоминал («что сделано?», «когда будет?», «напоминаю», «ещё раз прошу», «до сих пор», «есть новости?»).
- `client_days_without_reply`: рабочие дни, когда клиент писал по делу, а авитолог в этой группе за день не написал ни разу.
- `project_share`: какую долю сообщений сотрудников в его группах пишут проджекты. Большая доля значит, что проджект часто подключается вместо него.
- `signals`: сигналы за период в его группах по видам (раздел 4). `signals_on_own_messages`: сигналы о его собственных сообщениях, например о тоне общения с клиентом (`staff_tone`).

В `chats` те же цифры по каждой группе: кто авитолог (`avitolog`), кто проджект (`project`), кто из сотрудников сколько писал, `reminders` и `client_days_without_avitolog` (дни без авитолога в этой группе).

Пороги для тегов за 30 дней. Правила:

- Теги ставьте только сотрудникам с `role: "staff"`, проджектам не ставьте.
- Теги скорости ставьте, только если у сотрудника не меньше 10 посчитанных ответов (`reply.replies`), на меньшем числе цифры случайны.
- Теги «Мало общается», «Задерживает задачи» и «Требует много контроля» ставьте, только если `avitolog_of` не пуст. «В одной из его групп» значит: в `chats` есть строка, где `avitolog` совпадает с его `key`, и порог выполнен в этой строке.
- Если запрашиваете не 30 дней, счётчики (напоминания, дни, сигналы) пересчитайте пропорционально, а минуты и доли оставьте как есть.

| Тег | Когда ставить |
|---|---|
| Быстро отвечает | `reply.median_minutes` не больше 15 и `reply.over_1h_share` не больше 0,15 |
| Медленно отвечает | `reply.median_minutes` больше 60 или `reply.over_1h_share` от 0,3 |
| Мало общается, не выходит на связь | в одной из его групп `client_days_without_avitolog` от 3, или `waiting_now` от 2 в двух ежедневных запросах подряд (сохраняйте вчерашний ответ) |
| Задерживает задачи | в одной из его групп `reminders` от 2, или `signals.question_unanswered` от 2 |
| Требует много контроля | `project_share` от 0,4 и `reminders` от 2 (сумма по его группам) |
| Плохо общается с клиентами, конфликтный | в `signals_on_own_messages` есть хоть один сигнал, или `signals.negative` от 2 |

Пример ответа (сокращён):

```json
{
  "days": 30, "workdays": 23,
  "work_hours": {"start": "09:00", "end": "18:00", "timezone": "Europe/Moscow", "weekdays_only": true},
  "staff": [
    {
      "key": "@evgeniy", "name": "Евгений авитолог", "role": "staff", "messages": 270,
      "avitolog_of": [{"chat_id": "...", "title": "Кирпич", "client_name": null}],
      "active_workdays": 20,
      "reply": {"replies": 122, "median_minutes": 2.6, "p90_minutes": 133.3, "over_1h": 15, "over_1h_share": 0.12},
      "waiting_now": 2, "reminders": 2, "client_days_without_reply": 1, "project_share": 0.08,
      "signals": {"negative": 1}, "signals_on_own_messages": {}
    }
  ],
  "chats": [
    {"chat_id": "...", "title": "Кирпич", "project": "@smmaleksandr", "avitolog": "@evgeniy",
     "reply": {"replies": 60, "median_minutes": 3.0, "over_1h_share": 0.12}, "reminders": 1,
     "client_days_without_avitolog": 1}
  ],
  "possible_staff": [{"staff_key": "id:1202727565", "name": "Полина Авитолог", "messages": 148, "chats": 4}],
  "warnings": ["possible_staff"]

```

`warnings` может содержать `staff_empty` (сотрудники не отмечены), `projects_empty` (проджекты не указаны) и `possible_staff` (есть кого проверить).

Чего аналитика не видит: смысл работы (выполнена ли стратегия, качество материалов), личные сообщения, звонки и группы, где нет бота. Напоминания клиента ищутся по словам, просьбу, повторённую другими словами, она может пропустить.

### Характеристика текстом

`GET /monitor/staff-stats?with_summary=1` добавляет каждому сотруднику с `role: "staff"` поле `summary`: 5-8 предложений для руководителя. В нём сказано, как быстро сотрудник отвечает, в каких группах тянет, как часто клиенты напоминают и в какие дни сотрудник молчал, есть ли сигналы о тоне и что получается хорошо. Последнее предложение содержит вывод.

- Текст собирается только из цифр этого же ответа, переписку модель не читает. Каждое число в тексте есть среди цифр ответа. Оценки «быстро», «медленно», «задерживает задачи» поставлены по порогам из таблицы выше.
- О качестве материалов, бюджете, ставках и результатах клиентов текст не говорит: система их не видит.
- `summary_source`: `model`: текст написала модель, `template`: короткий текст по шаблону (данных мало или модель не ответила). `summary_at`: когда текст собран.
- Текст собирается раз в сутки (по московскому дню) и до конца суток отдаётся из кэша. Запрос с `with_summary=1` в первый раз за день отвечает дольше, до минуты. Без `with_summary` ответ прежний и быстрый.
- Проджектам `summary` не пишется (`null`).

## 5. Вебхук

Адрес вашего приложения указывается в кабинете: «Мониторинг чатов», блок «Куда отправлять сигналы», поле «Адрес вашего приложения (вебхук)». Адрес должен начинаться с `http://` или `https://`, рекомендуем HTTPS. Кнопка «Проверить» отправляет на адрес тестовое событие `signal.test`.

На каждый новый сигнал Assistych отправляет `POST` с телом JSON.

Заголовки:

| Заголовок | Значение |
|---|---|
| `Content-Type` | `application/json` |
| `X-Event` | `signal.created` (или `signal.test` для проверки) |
| `X-Signature` | `sha256=<hex>`: HMAC-SHA256 от сырого тела запроса, ключ: ключ API бизнеса |

Пример тела:

```json
{
  "event": "signal.created",
  "signal_id": "b6c1a3e2-0000-0000-0000-000000000000",
  "signal_type": "negative",
  "confidence": 0.86,
  "status": "new",
  "chat": {
    "id": "5f0e0000-0000-0000-0000-000000000000",
    "platform": "telegram",
    "telegram_chat_id": -1001234567890,
    "external_chat_id": -1001234567890,
    "title": "Ромашка / Агентство"
  },
  "client": {"name": "Ромашка"},
  "text": "за что мы вообще платим",
  "reason": "клиент недоволен результатом и сомневается в оплате",
  "link": "https://t.me/c/1234567890/5531",
  "sender": {"name": "Ирина", "username": "irina_r", "is_staff": false},
  "ts": "2026-09-28T09:41:07+00:00",
  "created_at": "2026-09-28T09:44:10+00:00",
  "cabinet_url": "https://assistych.ru/ru/chat-monitor?signal=b6c1a3e2-0000-0000-0000-000000000000",
  "project": "@smmaleksandr",
  "message_text": "Добрый день. Объявления до сих пор не вышли, за что мы вообще платим",
  "already_answered": {
    "name": "Александр",
    "username": "smmaleksandr",
    "at": "2026-09-28T09:42:30+00:00",
    "text": "Ирина, добрый день! Разбираемся, сегодня до обеда",
    "message_id": 18342
  }
}
```

Поля:

- `link` есть только у супергрупп Telegram. У обычных групп и у всех групп MAX он равен `null`.
- `client.name` равен названию, которое вы вписали у группы в кабинете, иначе `null`.
- `project` содержит проджекта группы на момент сигнала (раздел 4а) либо `null`, если проджект не определился.
- `text` — цитата, которую выбрала модель, иногда это часть сообщения. `message_text` — всё сообщение целиком, с расшифровкой голосового или описанием фото, если разбор включён. Показывайте его под пояснением `reason`.
- `already_answered` — первое сообщение сотрудника в группе после сообщения клиента и не позже создания сигнала: `name`, `username`, `at`, начало текста до 200 знаков `text`, `message_id`. Если никто не писал, `null`. У `staff_tone` всегда `null`. Сигнал при этом остаётся открытым: решает проджект.
- Для групп MAX `platform` равен `max`, поля `telegram_*` равны `null`, идентификатор группы берите из `external_chat_id`.
- Форма тела одинакова для всех видов сигналов.

Проверка подписи на Python:

```python
import hashlib, hmac

def valid(body: bytes, header: str, api_key: str) -> bool:
    expected = "sha256=" + hmac.new(api_key.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header or "")
```

Подпись считается от сырых байтов тела, поэтому читайте тело до разбора JSON.

Повторы. Ответ с кодом 2xx означает, что сигнал принят. Время ожидания ответа 10 секунд. При любом другом ответе или таймауте мы повторяем отправку через 1, 5, 15, 60 и 240 минут. После пятой неудачи сигнал в кабинете помечается «не доставлен в ваше приложение». Сам сигнал при этом остаётся доступным в API.

Идемпотентность. Повтор одного и того же сигнала возможен, если ваш сервер принял запрос, а ответ до нас не дошёл. Определяйте повтор по `signal_id`.

Как подтвердить обработку. Для приёма достаточно ответить 2xx. Для отметки о том, что проджект взял сигнал в работу или закрыл его, вызовите `PATCH /monitor/signals/{id}` (раздел 6).

Сверка на случай недоступности вебхука. Раз в 10 или 15 минут запрашивайте `GET /monitor/signals?status=new&since=<время последней сверки>` и создавайте задачи для сигналов, которых у вас ещё нет.

## 6. API

Базовый адрес: `https://assistych.ru/api/v1`.

Авторизация: заголовок `X-API-Key: <ключ API бизнеса>`. Ключ находится в кабинете: «Настройки», «Ключ API». Владелец может перевыпустить ключ, после этого старый перестанет работать, а подпись вебхука будет считаться новым ключом.

Лимит: 60 запросов в минуту на бизнес. В ответах есть заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. При превышении возвращается `429 RATE_LIMITED` с заголовком `Retry-After`. У загрузки истории `POST /monitor/import` отдельный лимит: 10 запросов в минуту.

Через API доступно всё, что есть на странице «Мониторинг чатов» в кабинете, кроме самой привязки группы (раздел 2). Ключ одного бизнеса не видит группы, сигналы и настройки другого. По ключу нельзя перевыпустить сам ключ, удалить бизнес или изменить что-то вне мониторинга.

Формат ошибки:

```json
{"detail": {"error": {"code": "NOT_FOUND", "message": "Чат не найден"}}}
```

Методы:

| Метод и путь | Назначение | Параметры |
|---|---|---|
| `GET /monitor/chats` | Список групп бизнеса | нет |
| `GET /monitor/chats/{id}/messages` | Сообщения группы по возрастанию времени | `limit` (1-200, по умолчанию 50); `before=<id сообщения>`: страница старше; `after=<id сообщения>`: новее. Без курсора: последние сообщения |
| `GET /monitor/signals` | Список сигналов, новые сверху | `status` (через запятую, например `new,in_work`); `signal_type` (через запятую); `chat_id`; `project` (`@ник` проджекта или `none`: без проджекта); `since` (время ISO: созданные или изменённые после); `limit` (1-200); `before=<id сигнала>`: следующая страница |
| `GET /monitor/signals/{id}` | Один сигнал | нет |
| `GET /monitor/senders` | Кто писал в группах: чтобы отметить своих в `staff` (раздел 4а) | `days` (1-365, по умолчанию 60); `chat_id` |
| `GET /monitor/staff-stats` | Аналитика по сотрудникам: скорость ответа, напоминания клиента, дни без ответа, сигналы; с `with_summary=1` характеристика каждого текстом (раздел 4б) | `days` (1-90, по умолчанию 30), `with_summary` (`1`, по умолчанию нет) |
| `PATCH /monitor/signals/{id}` | Отметить обработку | тело: `{"status": "new" \| "in_work" \| "done" \| "dismissed", "comment": "текст"}`; `comment` необязателен, до 2000 знаков |
| `GET /monitor/export/signals.csv` | Выгрузка сигналов в CSV | `since`, `until` (дата или время ISO, по умолчанию последние 30 дней); `signal_type`, `status` через запятую |
| `GET /monitor/export/chats.csv` | Сводка по группам за период в CSV | `since`, `until` |
| `GET /monitor/settings` | Настройки: ссылка и команда привязки, «наши», виды сигналов, адрес вебхука | нет |
| `PATCH /monitor/settings` | Изменить настройки | любые из полей: `staff` (юзернеймы `@name`, ссылки `t.me/...` или числовые id), `signal_types` (`negative`, `payment_due`, `report_request`, `question_unanswered`, `staff_tone`), `unanswered_hours` (1-72), `webhook_url` (`https://...`, пустая строка убирает адрес), `media_types` (`voice`, `photo`, `video`), `media_retention_days` (1-365), `projects` (ники проджектов, раздел 4а; `[]` значит все «наши»), `work_start` и `work_end` (рабочее время для `question_unanswered`, `"09:00"`, будни по Москве, начало раньше конца) |
| `POST /monitor/settings/rotate-code` | Новый код привязки | нет |
| `POST /monitor/webhook/test` | Отправить тестовый сигнал `signal.test` на адрес вебхука | нет |
| `PATCH /monitor/chats/{id}` | Название клиента, проджект группы, отключить или включить группу | тело: `{"client_name": "...", "project": "@ник" \| null, "status": "active" \| "disabled"}`, любое из полей; `project: null` возвращает автоматический выбор |
| `POST /monitor/import` | Загрузить историю одной группы | multipart: `file` (JSON экспорта Telegram Desktop, до 20 МБ), `final` (`false` для частей полного экспорта) |
| `POST /monitor/import/match` | Какие чаты полного экспорта подключены | тело: `{"chats": [{"id": 1234567890, "type": "private_supergroup"}]}`, до 500 чатов |
| `POST /monitor/import/finish` | Завершить загрузку полного экспорта | нет |

Основные поля ответов.

- Группа (`items[]` в `/monitor/chats`): `id`, `platform` (`telegram` или `max`), `external_chat_id`, `telegram_chat_id` (у MAX `null`), `title`, `chat_type` (`group` или `supergroup`), `status` (`active`, `left`: бота удалили, `disabled`: отключили в кабинете), `client_name`, `project` и `project_source` (`manual`, `auto` или `null`, раздел 4а), `bot_is_admin`, `sees_all_messages`, `open_signals`, `last_message_at`, `bound_at`.
- Сообщение: `id`, `external_message_id`, `telegram_message_id`, `sender` (`name`, `username`, `external_user_id`, `telegram_user_id`, `is_staff`), `text`, `kind` (`text`, `photo`, `voice`, `video`, `video_note`, `document`, `sticker`, `audio`, `animation`, `other`), `media`, `source` (`bot` или `import`), `sent_at`, `edited_at`, `link`. В ответе также есть `has_more`.
- Сигнал: `id`, `signal_type`, `status`, `confidence`, `text`, `reason`, `project`, `repeats`, `comment`, `chat`, `sender`, `message_id`, `link`, `ts`, `delivery` (`none`, `pending`, `sent`, `failed`), `delivery_attempts`, `delivery_error`, `created_at`, `updated_at`, `closed_at`, `message_text`, `already_answered` (оба как в вебхуке, раздел 5), `auto_closed` (`true`, если сигнал закрыла система, а не человек). В списке также есть `has_more`.

Коды ошибок:

| Код | Когда |
|---|---|
| `401 API_KEY_INVALID` | неверный или отсутствующий ключ |
| `404 NOT_FOUND` | группа или сигнал не найдены либо принадлежат другому бизнесу |
| `400 INVALID_ID` | идентификатор не является корректным UUID |
| `400 INVALID_URL` | адрес вебхука не начинается с `http://` или `https://` |
| `400 NO_WEBHOOK` | проверка вебхука, а адрес не задан |
| `400 INVALID_PROJECT` | в `project` у группы передано несколько ников |
| `400 INVALID_WORK_HOURS` | `work_start` не раньше `work_end` |
| `404 CHAT_NOT_CONNECTED` | группа из файла истории не подключена к вашему бизнесу |
| `400 FILE_TOO_LARGE`, `400 BAD_FILE`, `400 FULL_ACCOUNT_EXPORT` | файл истории больше 20 МБ, не JSON-экспорт Telegram Desktop или экспорт всего аккаунта вместо одной группы |
| `409 OPEN_SIGNAL_EXISTS` | сигнал нельзя вернуть в `new` или `in_work`, пока по группе открыт другой сигнал того же вида |
| `422` | неверное тело запроса или параметры |
| `429 RATE_LIMITED` | превышен лимит запросов |

Примеры запросов.

Список открытых сигналов:

```
curl -H "X-API-Key: $ASSISTYCH_API_KEY" \
  "https://assistych.ru/api/v1/monitor/signals?status=new,in_work&limit=50"
```

Последние 30 сообщений группы:

```
curl -H "X-API-Key: $ASSISTYCH_API_KEY" \
  "https://assistych.ru/api/v1/monitor/chats/<chat_id>/messages?limit=30"
```

Взять сигнал в работу:

```
curl -X PATCH -H "X-API-Key: $ASSISTYCH_API_KEY" -H "Content-Type: application/json" \
  -d '{"status": "in_work"}' \
  "https://assistych.ru/api/v1/monitor/signals/<signal_id>"
```

Закрыть сигнал с комментарием:

```
curl -X PATCH -H "X-API-Key: $ASSISTYCH_API_KEY" -H "Content-Type: application/json" \
  -d '{"status": "done", "comment": "созвонились, вопрос решён"}' \
  "https://assistych.ru/api/v1/monitor/signals/<signal_id>"
```

Ссылка и команда привязки для проджекта:

Файлы в сообщениях. Если в группу прислали фото, голосовое, видео или документ, у сообщения заполнено поле `media`:

```json
"media": {
  "kind": "voice",
  "state": "stored",
  "url": "/api/v1/files/monitor/2026-09/5c1e..._voice.m4a?exp=1790000000&sig=...",
  "mime": "audio/mp4", "size": 18432, "duration": 7,
  "files": [{"url": "...", "mime": "audio/mp4"}],
  "analysis": "done",
  "text": "[Голосовое: пришлите отчёт за сентябрь, пожалуйста]"
}
```

- `kind`: `photo`, `voice`, `audio`, `video_note` (кружок), `video`, `document`. Стикеры и гифки не сохраняются.
- `state`: `pending` (загружается), `stored` (файл есть, заполнен `url`), `too_large` (больше 20 МБ), `evicted` (удалён, чтобы освободить место), `quota`, `no_space`, `failed`, `expired` (удалён по сроку хранения), `unavailable` (из экспорта Telegram Desktop). Любое незнакомое значение считайте как «файла нет».
- `url` относительный к `https://assistych.ru`, подписанный и действует сутки. Нужен файл позже: запросите сообщения заново.
- `analysis` показывает разбор ИИ, если он включён в кабинете: `pending`, `done`, `failed`, `limit`, `skipped`, `too_large`, `null`. В поле `text` при `done` лежит расшифровка речи или описание фото. Этот же текст видит классификатор, поэтому голосовое «где отчёт?» даёт сигнал `report_request`.
- По умолчанию файлы хранятся 30 дней, на бизнес выделено 2 ГБ. Когда место кончается, удаляются самые старые файлы. Сообщения остаются.

Выгрузка CSV. Формат рассчитан на русский Excel: UTF-8 с BOM, разделитель `;`, время московское, не больше 20 000 строк за запрос. Колонка «Проджект» содержит ник без `@`. Новые колонки добавляются в конец, прежние остаются на местах: в выгрузке сигналов после «Проджекта» идут «Сообщение целиком» и «Уже ответил», в сводке по группам после «Проджекта» идёт «Тон сотрудника». В Google Таблицах используйте «Файл», «Импорт», «Загрузить» и укажите разделитель «точка с запятой».

## 7. Инструкция для разработчика приложения

Техническое задание на подключение сигналов Assistych к таск-менеджеру.

1. Создайте публичный HTTPS-эндпоинт приёма вебхука, например `POST /webhooks/assistych`. Адрес укажите в кабинете Assistych (раздел 5).
2. Храните ключ API в переменной окружения `ASSISTYCH_API_KEY`. В исходный код ключ не вписывайте.
3. Читайте тело запроса как сырые байты до разбора JSON. Проверьте подпись `X-Signature` по алгоритму из раздела 5, сравнение выполняйте за постоянное время. При несовпадении подписи верните 401 и ничего не создавайте.
4. Обработайте `X-Event`: для `signal.test` верните 200 без действий, для `signal.created` создайте задачу.
5. Обеспечьте идемпотентность: если задача с таким `signal_id` уже существует, верните 200 и не создавайте вторую. Сохраняйте `signal_id` в задаче.
6. Формируйте задачу по `signal_type`. Заголовок: `Негатив: ...`, `Оплата: ...`, `Отчёт: ...`, `Ждёт ответа: ...`, `Тон сотрудника: ...`, дальше `client.name`, а если он пуст, `chat.title`. Для любого другого значения `signal_type` используйте заголовок `Сигнал: ...` и всё равно создайте задачу, потому что виды могут добавляться. В теле задачи укажите цитату `text`, причину `reason`, сообщение целиком `message_text`, автора `sender.name`, время `ts`, ссылки `link` (может быть `null`) и `cabinet_url`. Если `already_answered` не `null`, покажите «Уже ответил: имя, время, начало ответа».
7. Отвечайте 2xx быстро, в течение 10 секунд, а тяжёлую работу выполняйте после ответа. При других ответах Assistych повторит отправку по графику из раздела 5.
8. Возвращайте статус обработки через `PATCH /monitor/signals/{signal_id}`: `in_work`, когда проджект взял задачу; `done`, когда решено; `dismissed`, когда это ложное срабатывание. Закрывайте сигнал вместе с задачей: пока сигнал открыт, новые случаи того же вида в этой группе не создают отдельных задач. Ответ `409 OPEN_SIGNAL_EXISTS` при возврате старого сигнала означает, что по группе уже открыт новый: работайте с ним.
9. Добавьте сверку раз в 10 или 15 минут по `GET /monitor/signals?status=new&since=...` с постраничным чтением через `before=<id последнего элемента>`, пока `has_more` равно `true`.
   Если показываете открытые сигналы опросом `status=new,in_work`, учтите: `question_unanswered` закрывается сам после ответа сотрудника и пропадает из этого списка. Закрытые за неделю берите запросом `GET /monitor/signals?status=done,dismissed&since=<7 дней назад>` (`since` учитывает и время закрытия), автоматически закрытые отличаются полем `auto_closed: true`.
10. По желанию показывайте в задаче 10-20 последних сообщений группы (`GET /monitor/chats/{chat.id}/messages?limit=30`) и текст `media.text` рядом с сообщением. Не сохраняйте `media.url` надолго, он действует сутки.

Соблюдайте лимит 60 запросов в минуту и при ответе 429 ждите `Retry-After` секунд. Через API читаются данные, отмечаются статусы и меняются настройки мониторинга (раздел 6), писать в группы от имени Assistych через него нельзя.

## 7а. WhatsApp и переписка во внешней системе

Для системы, которая показывает переписку у себя (например, система учёта). Всё по тому же ключу `X-API-Key`, кабинет не нужен. WhatsApp включает для бизнеса администратор Assistych, без этого ручки `/monitor/whatsapp` отвечают 404.

```bash
K="X-API-Key: <ключ>"; A=https://assistych.ru/api/v1/monitor

# привязать номер: показать QR человеку, опрашивать раз в 2-3 секунды до status = open
curl -s -X POST -H "$K" $A/whatsapp/connect
curl -s -H "$K" $A/whatsapp

# чаты номера и выбор рабочих (полная замена набора, до 500); к нам попадают только выбранные
curl -s -H "$K" $A/whatsapp/chats
curl -s -X PUT -H "$K" -H 'Content-Type: application/json' \
  -d '{"chats": ["120363025@g.us", "79991234567@s.whatsapp.net"]}' $A/whatsapp/selection

# список чатов для экрана (все мессенджеры), у каждого last_message
curl -s -H "$K" $A/chats

# переписка чата постранично, назад через before=<id первого сообщения страницы>
curl -s -H "$K" "$A/chats/<id чата>/messages?limit=50"

# новые сообщения всех чатов: первый вызов даёт next_after, дальше опрашивать с ним раз в 10-30 секунд
curl -s -H "$K" "$A/messages"
curl -s -H "$K" "$A/messages?after=<next_after>&platform=whatsapp"

# одно сообщение: свежая ссылка на файл или файл, который был в состоянии pending
curl -s -H "$K" "$A/messages/<id сообщения>"
```

Вместо опроса ленты можно получать новые сообщения вебхуком. Включите его отдельно от сигналов:

```bash
curl -s -X PATCH -H "$K" -H 'Content-Type: application/json' \
  -d '{"webhook_url": "https://example.ru/hooks/assistych", "message_events": true}' $A/settings
```

Раз в минуту на адрес приходит `POST` с `X-Event: messages.created` и телом `{"event": "messages.created", "items": [...]}`, до 50 сообщений в пачке, поля как у ленты. Подпись `X-Signature` проверяется так же, как у сигналов (раздел 5). Если вы не ответили 2xx, та же пачка придёт в следующую минуту. Дубли убирайте по `id` сообщения. В вебхук и ленту попадают только новые сообщения: старую переписку, загруженную при выборе чата, читайте постранично по чату. Лента отстаёт от реального времени примерно на 10 секунд.

Ответить в WhatsApp через API нельзя. Шлюз Assistych только читает переписку, так меньше риск, что WhatsApp заблокирует номер. Ответ пишут с телефона, он появится в переписке с пометкой `is_staff: true`.

## 8. Ограничения и что дальше

Сейчас поддерживаются группы Telegram и MAX, а также чаты WhatsApp, если администратор Assistych включил его для бизнеса (раздел 7а).

- Бот видит сообщения с момента добавления. Более раннюю переписку Telegram можно загрузить экспортом, у MAX такой возможности нет.
- Привязывать группу может только её администратор. Группа привязана к одному бизнесу.
- Документы (pdf, docx, xlsx) сохраняются и скачиваются, но ИИ их не разбирает.
- Файлы больше 20 МБ не сохраняются.
- Интеграции с Google Таблицами нет, есть выгрузка CSV.
- Шаблонные сообщения клиентам в группы (например, напоминание об оплате) пока не делаем: для них нужны правила от агентства.

Этап 2: шаблонные напоминания, когда будут согласованы правила.

## Приложение А. Пример полного цикла

1. В группе «Ромашка / Агентство» клиент Ирина пишет: «за что мы вообще платим». Бот читает сообщение.
2. Через 3 минуты тишины в группе пачка сообщений уходит на разбор. ИИ определяет недовольство, `signal_type` равен `negative`, `confidence` равен 0,86.
3. Assistych создаёт сигнал и отправляет `POST` на адрес вашего приложения с заголовками `X-Event: signal.created` и `X-Signature: sha256=...`.
4. Приложение проверяет подпись, не находит `signal_id` среди существующих задач, создаёт задачу «Негатив: Ромашка» с цитатой, причиной и ссылками, и отвечает 200.
5. Проджект открывает задачу, нажимает «Взять в работу». Приложение вызывает `PATCH /monitor/signals/{signal_id}` с телом `{"status": "in_work"}`. В кабинете Assistych сигнал получает статус «В работе».
6. Проджект связывается с клиентом и закрывает задачу. Приложение вызывает `PATCH` с телом `{"status": "done", "comment": "созвонились, вопрос решён"}`. Сигнал закрыт, следующий негатив в этой группе даст новую задачу.
7. Если на шаге 4 приложение было недоступно, Assistych повторил бы отправку через 1, 5, 15, 60 и 240 минут, а сверка по `GET /monitor/signals?status=new` подобрала бы сигнал.
